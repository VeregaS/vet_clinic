# Защита при развёртывании

Compose в корне запускает локальное HTTP-демо. Для внешнего сервиса используйте
`DJANGO_SETTINGS_MODULE=config.settings_production`, рабочий WSGI/ASGI-сервер
и HTTPS на обратном прокси. Запускайте Django на закрытом адресе. Раздавайте
результат `python manage.py collectstatic --noinput` с прокси.
Профиль отключает DEBUG, включает Secure для cookies и перенаправление на HTTPS.
Включайте HSTS для дополнительных доменов только после проверки TLS на них.

Если TLS завершает прокси, установите `TRUST_PROXY_HEADERS=true`. Прокси должен
отбрасывать клиентские значения `X-Forwarded-Proto` и `X-Real-IP` и устанавливать
собственные. Прямой доступ клиента к Django в этом режиме запрещён.
Профиль требует `DB_SSL_ROOT_CERT` с путём к корневому сертификату PostgreSQL
и проверяет сертификат и имя сервера. Для `DB_HOST` используйте имя из сертификата.

## Роль приложения в PostgreSQL

Сначала проверьте восстановление резервной копии на отдельной БД. Миграции
выполняйте от имени владельца схемы. Затем в выделенной БД клиники подключитесь
этой же ролью через `psql` и примените `deploy/provision_app_role.sql`. Команда
создаёт `vetclinic_app` и запрашивает пароль интерактивно. Она рассчитана на
однократное применение. Если роль уже существует, проверьте её права отдельно.

Задайте серверу Django `DB_USER=vetclinic_app` и её пароль из хранилища секретов.
Учётные данные владельца схемы выдавайте только процессу миграций.
Запустите `python manage.py check --deploy --fail-level ERROR` под ролью приложения.
Если схема унаследовала разрешение CREATE для PUBLIC, снимите его после проверки
других пользователей этой БД. Проверьте вход, запись, кабинет и PDF после смены роли.

В локальном Compose с уже заполненной БД можно оставить исходные учётные данные
PostgreSQL в `DB_OWNER_USER` и `DB_OWNER_PASSWORD`, а для веб-приложения задать
`DB_USER=vetclinic_app` и её пароль. Compose не передаёт значения `DB_OWNER_*`
веб-контейнеру. Для новых миграций разово передавайте владельца через
`docker compose run --rm -e DB_USER -e DB_PASSWORD web python manage.py migrate`,
подставив значения через переменные окружения процесса. Тесты запускайте на
отдельной PostgreSQL под ролью, которой разрешено создавать тестовую базу.

Правила доступа к строкам пока действуют в Django. Перед добавлением RLS нужно
спроектировать передачу идентификатора сотрудника внутри транзакции и отдельно
проверить публичное бронирование, администратора, задачи обслуживания и PDF.
Для защиты данных на диске нужны проверенные шифрование томов и резервных копий
и правила хранения ключей. TLS защищает соединение с БД.

## Лимиты и секреты

Приложение хранит общие для всех рабочих процессов счётчики в PostgreSQL. Вход
в кабинет и Django admin делят лимит в 10 POST за 5 минут на IP. Запись на приём
ограничена 10 POST за 10 минут на IP. При отказе возвращается 429 с Retry-After.
Публичная форма также содержит поле-ловушку для простых ботов. Перед открытием
формы в интернет настройте лимиты на прокси и проверку контакта, если это нужно
по правилам клиники.

Исторический ключ Django и пароль PostgreSQL считайте раскрытыми. Смените их
во всех экземплярах, где они ещё используются. Очистка публичной истории
потребует отдельного окна для координации с владельцами веток, клонов и форков.
Храните рабочие секреты вне Git и отдельно от резервных копий.
